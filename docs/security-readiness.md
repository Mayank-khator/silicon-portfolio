# Security readiness and deployment boundaries

**Assessment date: 27 September 2026. Scope: synthetic management demo and enterprise foundation.** This repository is not a certified system or an approved store for production semiconductor IP. Feature presence, source review, a passing unit test, and a tested deployment are distinct forms of evidence.

## Two distinct trust boundaries

The static demo serves fictional data and saves edits in browser storage. Its role controls and audit view illustrate workflows; a browser user can inspect and change local state. It provides no trusted authentication, tenant isolation, durable shared audit trail, or recovery guarantee. Use a dedicated browser profile for the presentation and clear demo storage afterward when needed. Do not enter real data.

The connected architecture uses Supabase authentication and database policies, with authenticated requests through FastAPI and Kong. It needs actual provisioning, secrets, migrations, access testing, and an operator before it is a secure shared service. A successful frontend build does not prove this path. Container startup, network configuration, deployed PostgreSQL policies, Realtime permissions, and end-to-end auth remain integration checks on the target environment.

## Source review and recorded verification

The following controls are present in the reviewed source: [user-token validation and forwarding](../services/shared/supabase.py), [strict request validation](../services/shared/models.py), [version-filtered API writes](../services/shared/crud.py), [RLS, domain guards, audit triggers and worker RPCs](../supabase/migrations/202609270001_initial.sql), [outbox delivery](../services/worker/outbox.py), and [optional AI gates/fallback](../services/agentic_ai/app.py).

Component-owner verification recorded on 27 September 2026 reports **38 passing backend tests** and **58 passing database assertions**. Backend tests use mock responses for the external Supabase HTTP boundary. The [database runner](../supabase/tests/run.mjs) executes the migration and [security assertions](../supabase/tests/security.sql) in PGlite PostgreSQL, supplying test implementations of Supabase identity functions and roles. These are useful checks of executable SQL, not evidence of live Supabase Auth, PostgREST, Realtime, independent concurrent connections, RabbitMQ, or Docker deployment. This documentation review did not rerun those already completed suites.

The checked-in [Python dependency audit](../services/dependency-audit.json) records no known vulnerabilities for the listed runtime packages at that check. It does not cover optional LLM dependencies, container operating-system packages, application logic, or vulnerabilities discovered later.

## Control and evidence matrix

“Implemented” below means present in reviewed source. The last column identifies deployment evidence or additional work still required; source presence alone is not an operational-security claim.

| Area | Implemented control / current boundary | Evidence required before a real-data pilot |
| --- | --- | --- |
| Authentication | Each domain API calls Supabase `/auth/v1/user`, then forwards the same user token to PostgREST. There is no API service-role fallback. Missing/invalid identity fails closed; upstream redirects are disabled. `/health` is unauthenticated liveness only. | Verify deployed token expiry/revocation, logout, recovery, approved MFA/SSO design, and the configured Supabase endpoint. |
| Authorization and tenancy | RLS checks database membership/roles; immutable tenant IDs and composite foreign keys constrain relationships. Clients cannot create memberships, escalate roles, access outbox, or invoke worker RPCs. | Repeat the two-tenant/role checks through live Auth/PostgREST and confirm no privileged-key bypass in deployed API/frontend configuration. |
| Business integrity | API models reject unknown fields, invalid dates/numbers, future time dates and non-quarter-hour entries. SQL independently guards sequential stages, design freeze roles, time review/ownership, project/task dates and daily totals. API PATCH filters the expected version; an invoker-security SQL RPC also checks it. | Exercise concurrent connections. Direct authorized PostgREST writes can omit the expected-version filter; SQL also rejects future UTC dates and non-quarter-hour entries. Require expected-version filters or the version-checking RPC for direct authorized database writes. |
| Audit trail | SQL triggers write before/after values, actor and time in the mutation transaction. Privileges deny client insert/update/delete/truncate and direct service-role audit insertion; triggers reject updates/deletes/truncation. Local demo history is editable. | Verify deployed privileges and actor attribution. Database owners can change triggers/grants; privileged workers can bypass domain RLS. Use separately controlled retention for stronger tamper resistance. |
| Transport encryption | APIs set `no-store` and `nosniff`, disable public API docs, and use configured CORS origins. Local HTTP is not TLS evidence; frontend HTTPS does not secure a separately exposed API/broker. | Verify HTTPS/certificate renewal, ingress policy, exact CORS origins, and protected database/broker paths. Prevent public access around Kong. |
| Encryption at rest | Docker volumes and PostgreSQL storage are **not encrypted by this repository**. | Configure and verify host/disk/database/backup encryption, key ownership and rotation. Managed-host encryption is a vendor control whose scope must be checked. |
| Secrets | Environment templates are configuration aids, not a vault. Publishable Supabase keys still require correct RLS. | Scan repository/history/build artifacts; inject secrets through an approved secret store; rotate sample/default credentials; keep service keys only in trusted server jobs. |
| Event delivery | Audit and outbox rows share a transaction. Worker RPCs lease events and enforce owner acknowledgement/retry limits. Publisher uses durable exchange/queue, persistent messages and broker confirms before SQL acknowledgement. Delivery is at least once. | Test with a real broker: restart, duplicates, dead events, retention, consumer deduplication, and backlog alerts. Broker management ports and credentials need protection. |
| Realtime | Migration publishes tenant-readable domain/audit tables and excludes the worker outbox. Publication alone does not prove channel authorization or revocation behavior. | Verify tenant-filtered subscriptions, revoked users, reconnects, and stale-write conflicts against the live deployment. |
| AI | Default provider is `none`; report requests must opt in separately. Groq also requires `ALLOW_EXTERNAL_LLM=true`. Only aggregate report metrics go into the optional prompt; timeout/provider failure preserves the deterministic report. No agent mutates projects. | Verify endpoint/model license and local-only settings. Aggregate budgets can still be sensitive. Restrict egress, disable tracing, review outputs, and validate real provider/failure behavior before enabling inference. |
| Supply chain | Dependency files and containers identify inputs; they do not establish absence of vulnerabilities. | Lock versions, inventory licenses, scan dependencies/images and secrets, patch critical issues, record build provenance, and review CI/deployment permissions. |
| Availability and recovery | Browser storage, a source repository, and a running container are not backups of business data. | Define RPO/RTO, encrypted off-site backups, retention/deletion rules, restore drills, monitoring, incident ownership, and a rollback procedure. |

Supabase explicitly leaves application design, accounts, data access, secrets, and security configuration with the customer. Its infrastructure controls do not certify this application. [Shared responsibility](https://supabase.com/docs/guides/deployment/shared-responsibility-model), [vendor security](https://supabase.com/security). Use the [OWASP Application Security Verification Standard](https://owasp.org/projects/asvs) to structure an independent application assessment appropriate to the pilot's risk.

## Operator configuration

1. Keep the public preview synthetic and API-disconnected. Display demo mode clearly. Review source, fixture data, exports, and frontend environment variables before publishing.
2. Create an isolated connected test environment with fresh credentials. Apply migrations and synthetic seed, then execute database, API, UI, and Realtime authorization tests. Record command, version/commit, date, result, and test environment; mark skipped tests as skipped.
3. Terminate HTTPS at a managed ingress or configured reverse proxy. Bind database, broker, management interfaces, worker, and model ports to private networks. Configure a least-privilege service identity per job and restrict CORS to the intended frontend origins.
4. Configure encryption and backups explicitly. Free Supabase projects do not include managed automatic backups: use regular `supabase db dump` exports and protected off-site retention, and separately cover storage objects/configuration/secrets as appropriate. Test restoration. [Supabase backups](https://supabase.com/docs/guides/platform/backups).
5. For local-only Ollama, set `OLLAMA_NO_CLOUD=1` (or the documented equivalent), restart and verify cloud-disabled status; keep the endpoint private. Ollama's current runtime can also use cloud models and web search, so installing it is not evidence of local-only processing. [Ollama FAQ](https://docs.ollama.com/faq). Keep LangChain tracing and any remote model/provider integrations disabled unless explicitly approved for the data.
6. Put owners and alerting behind access reviews, vulnerabilities, availability, queue failures, quotas, and incident response. Free-plan pausing/quotas and limited recovery can interrupt a demonstration; keep a local synthetic fallback. [Supabase pausing](https://supabase.com/docs/guides/platform/free-project-pausing), [Cloudflare limits](https://developers.cloudflare.com/pages/platform/limits/).

## Acceptance record

Store evidence with the release: commit and deployed version; test logs including unexecuted suites; URL and TLS check; two-tenant access results; ordinary-user audit-tamper results; backup/restore record; secret and dependency scan results; approved data classification/region/vendor terms; and named service/security/quality owners. Until that record exists, describe the result as a **demonstration and implementation foundation**, not enterprise-certified, audit-proof, production-ready, or compliant with a regulated standard.

Automotive and medical quality use needs organization-specific validation and controlled traceability. Do not use demo gate approvals or event timestamps as regulated electronic signatures. See [legal-and-hosting.md](legal-and-hosting.md) for licensing, ownership, export-control, and regulatory boundaries.
